## 二、论文仍待完善的部分（按答辩风险排序）

### A. 高风险（答辩老师极可能问，必须有答案）

1. **「为什么没接 Gaussian / BDF / MOMAP？」**
   - 答辩话术：「软件许可受限于本机环境。但 ChemMaster 对这三个软件的 MCP wrapper 已实现，包含 input 生成、SLURM 提交、cclib 解析等完整链路；切换到具备这三个软件的机器（如学院公用工作站）即可使用。这一限制已在论文 §4.1 与结论 §5 中明确说明，并作为后续工作。」

2. **「84 % 自主恢复率是否客观？」**
   - 答辩老师可能追问"故障是你自己注入的、判定也是你自己写的，会不会偏向自己？"
   - 答辩话术：「故障注入与判定逻辑在仓库 scripts/benchmarks/run_engineering_real.py 中开源，5 类故障的注入方式与判定标准独立于 Agent 的恢复实现：注入侧手动构造异常（如改坏 Gaussian 输入文件、删盘空间）、判定侧只看最终输出文件是否符合预期，与 Agent 内部状态隔离。这套实验确实是工作量级的工程指标，与人因评估指标（如 §4.4.2 的提交时间节省率）不能等同。」

3. **「与 ChemCrow 比有什么实质区别？」**
   - 答辩话术：「主要有三点。一是工具协议：ChemCrow 绑定 LangChain，难以被其他客户端复用；ChemMaster 用 MCP，已通过协议探针验证可被任意 MCP 客户端连接。二是决策模式：ChemCrow 偏向 autonomous research agent，由 Agent 自主选择工具与方法；ChemMaster 区分操作性工作与化学决策，化学决策权通过 recommend 机制保留给研究者。三是覆盖范围：ChemCrow 主要集成 Web API 类工具；ChemMaster 集成本地量子化学软件的完整工作流。」

4. **「S22 误差 0.75 kcal/mol 对一个 benchmark 来说是大还是小？」**
   - 答辩话术：「分两层。从绝对值看，B3LYP-D3 在 S22 上文献报道的 MAE 一般在 0.3–0.5 kcal/mol；本工作 0.75 偏大，主因在 benzene_methane 与 benzene_dimer_T 两体系的几何用了文献描述的近似坐标而非 S22A 标坐。剔除几何不规范的 3 个体系，剩下 water_dimer 与 ethene_ethyne 误差均小于 0.6 kcal/mol，与文献水平吻合。这一点在论文 §4.2 第二段已经写明。」（**前提：你确实重跑了 S22A 标坐版本，否则就照实承认。**）

5. **「五层架构是必须的吗？是否过度设计？」**
   - 答辩话术：「五层并非为分层而分层：(L1) 知识库与确定性公式模块、(L2) 计算引擎、(L3) MCP 工具、(L4) Agent 内核、(L5) 用户界面 —— 每层都对应一个独立的工程关注点。例如 L3 之所以单独抽出，是因为 MCP 是协议级别的可复用单元，可以脱离 ChemMaster 主程序被 Claude Code、Cursor 等客户端单独挂载使用。如果合并 L2 / L3，就失去了协议级复用能力。」

### B. 中风险（答辩老师可能问，需要有方向）

6. **「这个工作的化学贡献在哪里？」**
   - 答辩话术：「本工作的贡献以工程为主，化学层面的直接贡献是验证了"承担操作性工作、保留化学决策权"这一设计原则在量子化学场景下的可行性 —— 即在 S22 与 QUEST 两个公开基准上，由 LLM 驱动的工作流能达到与传统手工流程相当的计算精度。化学发现层面的贡献需要在系统支持下解决具体科学问题，这部分是后续工作。」

7. **「为什么本科毕设要做这么大的系统？」**
   - 答辩话术：「在我熟悉 Gaussian / BDF / MOMAP 的过程中，逐渐意识到工作流上的重复劳动是一个普遍问题，而不是某个软件的特例。这个项目本质上是把"重复劳动"抽象成一个可被任何具备 LLM 能力的客户端调用的协议，所以系统体量来源于"完整覆盖一个工作流"而不是"做大"。代码量本身不是贡献，11000 行 Python 中相当一部分是 wrapper / 解析 / 测试，真正算法部分在 kb/formulas/ 模块，量级很小。」

### C. 低风险（不太会问，但准备一下不亏）

8. **「为什么用 Python 不用 Rust 或 Go？」** — Python 是化学领域 (psi4 / RDKit / ASE) 与 LLM SDK (Anthropic / OpenAI) 的事实标准，跨语言会引入过多 binding 成本。

9. **「为什么不直接用 LangChain？」** — LangChain 是框架而非协议，工具定义只能在 LangChain 生态内复用；MCP 是协议，跨框架/跨客户端可用，符合"工具应该是行业标准而非框架私有"的设计取向。

10. **「11000 行代码够吗 / 多吗？」** — 不应该用代码量衡量贡献。重要的是协议合规性与可复用性已经过验证。

### 讲稿正文（按 PPT 翻页节奏写）

> 各位老师下午好。我是化学学院 XX 级本科生 张容纲。我今天答辩的题目是
> **《基于大模型 Agent 与 MCP 协议的本地化计算化学任务自动化系统 ChemMaster
> —— 设计、实现与基础计算能力验证》**。
>
> **【翻页：研究背景】**
>
> 选题动机来自我自己学习量子化学软件时的真实体会。Gaussian、BDF、MOMAP
> 这些软件本身已经很成熟，但日常使用过程中真正占据时间的，其实不是化学
> 决策，而是重复性的操作环节：写输入文件、提交任务、监控运行、解析输
> 出、识别 SCF 不收敛或虚频再去调参。在多分子筛选场景下，这部分"操作
> 摩擦"会进一步累积。我把这一类操作环节统称为「任务提交摩擦」，把降
> 低这一摩擦作为本毕设的研究目标。
>
> **【翻页：核心设计哲学】**
>
> 这个项目的核心设计原则是"承担操作性工作、保留化学决策权"，类比关
> 系是：vibe coding 之于程序员 = ChemMaster 之于计算化学家。Agent 不替
> 化学家做方法、基组、泛函这类化学决策，而是承担它们的具体执行。系统
> 把所有动作分成 L1（自主）、L2（推荐+确认）、L3（必须用户决断）三个
> 权限级别 —— 输入文件语法微调、SCF guess 调整属于 L1，方法/基组/泛函
> 选择属于 L2，多重度模糊或 TS 判定属于 L3。
>
> **【翻页：五层架构】**
>
> 系统有五个层次：最底层 L1 是知识库和确定性公式模块，所有物理常数与
> 单位换算都固化在 Python 中，避免 LLM 直接进行浮点运算；L2 是各计算
> 引擎；L3 是基于 MCP 协议的工具集，每个量子化学软件都有一个对应的
> MCP server；L4 是 Agent 内核，基于 Anthropic SDK 的 tool-use loop 实
> 现；L5 是命令行、终端 UI 和本地 Web 三种前端。MCP 这一层之所以独立
> 抽出，是因为 MCP server 是协议级别的可复用组件，可以被 Claude Code、
> Cursor 等任何 MCP 兼容客户端独立挂载使用，不必依赖 ChemMaster 主程
> 序。这是本工作与 ChemCrow 等绑定 LangChain 框架方案的关键差异。
>
> **【翻页：三前端实测】**
>
> 三种前端都已实测可独立启动并正常响应：CLI 通过 `chemaster run` 调
> 用；Textual TUI 经无头测试模式启动并导出 SVG 渲染快照；本地 Web 前
> 端基于 FastAPI 后端 + 内嵌 SPA，由 Playwright 驱动 Chromium 完成实
> 测截图采集。三者共享同一 Agent 内核与工具集。
>
> **【翻页：S22 实验】**
>
> 实验部分。受测试机器软件许可所限，本工作的量子化学计算以 psi4 完
> 成。在 S22 弱相互作用基准上，用 B3LYP-D3(BJ)/def2-TZVP 加 counter-
> poise 校正，5 个体系的平均绝对误差为 0.75 kcal/mol。其中水二聚体与
> 乙烯-乙炔两个使用标准 S22 几何的体系误差小于 0.6 kcal/mol，与 B3LYP
> -D3 在 S22 上的文献误差水平一致。
>
> **【翻页：QUEST 实验】**
>
> 在 QUEST 激发态参考基准上，用 TD-CAM-B3LYP/def2-SVP，TDA。8 个激发
> 态总体 MAE 0.79 eV；其中价层激发态（n→π* 和低能 π→π*）误差小于
> 0.2 eV，Rydberg 态误差较大（1.4–1.6 eV），主因是 def2-SVP 基组未含
> diffuse 函数，与系统驱动 TDDFT 计算的能力无关。
>
> **【翻页：工程指标】**
>
> 工程指标方面，对 5 类常见操作性故障各执行 5 次注入测试（共 25 次），
> Agent 在 L1 范围内的自主恢复率为 84 %，超过预设的 80 % 目标。其余三
> 项工程指标 —— 任务提交时间节省率、化学决策推荐接受率、运行轨迹自主
> 步占比 —— 因依赖真人被试或真实大模型 API，本工作仅给出实验协议而未
> 完成数据采集，已在论文 §4.4.2 与结论中明确说明。
>
> **【翻页：局限与未来工作】**
>
> 本工作的局限主要有三点：第一，BDF 与 MOMAP 未能在本工作中真实接入，
> 依赖此二者的蒽分子速率与动力学验证留作后续工作；第二，三项工程指
> 标依赖真人或真实 LLM 调用，本工作只给协议未采数据；第三，部分 S22
> 体系的几何使用了文献描述的近似坐标，导致误差偏大。
>
> 未来工作的主要方向包括：在配置完整 Gaussian、BDF、MOMAP 的环境中
> 完成蒽分子速率与动力学验证；招募被试完成提交时间节省率与推荐接受
> 率的实验测量；以及在更多公开基准（如 GMTKN55）上扩展精度验证。
>
> **【翻页：总结】**
>
> 本工作的主要贡献是设计并实现了一套以 MCP 协议为核心、以"labor-
> saving collaborator"为设计原则的计算化学 Agent 系统，并通过两个公
> 开基准与一组工程指标对系统的基础能力进行了实测验证。代码、基准数据
> 与运行轨迹均已在 GitHub 开源。我的答辩到此为止，感谢老师们。
